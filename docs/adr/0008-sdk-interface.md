# ADR 0008: SDK interface ergonomics (session-less happy path)

## Status
Accepted.

## Context
The native (Swift/Kotlin) SDK and the cloud streaming client both exposed the
session/thread id to the caller — in the native `SdkAgentConfig` constructor
and in the cloud URL path (`POST /v1/sessions/:id/runs/stream`). That is more
verbose than the upstream ergonomics we want to match:

* The **OpenAI Agents SDK** quickstart runs `Runner.run(agent, input)` with no
  explicit session/thread object in the happy path; the platform manages
  conversation scope internally.
* The **codex** agents SDK follows the same shape: create an agent, call `run`
  with input, get a result — conversation continuity is handled by the
  harness, not by a caller-managed session id.

Our SDK forced callers to mint a session and thread its id through every call,
which conflicts with that goal and with rule 10 (the frozen OpenAI Responses
wire contract, where the caller should only speak `response.*`).

## Decision
* **Session is an internal memo-scope key, not a public constructor argument.**
  `create_agent` (native FFI) no longer takes a session; the returned `SdkAgent`
  owns an opaque session exposed only via `agent.session()` / `agent.sessionId()`
  for callers that need it. The happy path is `create_agent(name, model)` →
  `agent.run(input)` / `agent.run_stream(input)`, mirroring the OpenAI/codex
  `Runner.run(agent, input)` shape.
* **Cloud session is server-minted and hidden behind a thin client.** A session
  id is an opaque memo-scope string returned by `POST /v1/sessions`
  (`{ "id": <uuid> }`). The canonical cloud ergonomics is a hand-written
  `AriaCloudClient` (one per platform, NOT generated by UniFFI) exposing
  `createSession() -> String` plus `runStream(session, input, onEvent)` that
  builds the `/v1/sessions/:id/runs/stream` URL and forwards OpenAI
  `response.*` frames. Callers mint once and reuse the id for multi-turn runs;
  they never construct the URL by hand.
* **The REST contract is unchanged.** `POST /v1/sessions/:id/runs/stream`
  (and the blocking `POST /v1/sessions/:id/runs`) stay exactly as in rule 10.
  Only the SDK surface abstracts the session id away; wire frames are still
  frozen OpenAI Responses events.
* **Session ids are arbitrary stable strings.** The server does not require
  pre-creation (`memo` is lazy per session key), but `POST /v1/sessions` is the
  canonical mint for callers that want a server-assigned uuid. `"default"`,
  a user id, or any stable key is also valid.

## Consequences
* The happy path matches the OpenAI Agents SDK / codex ergonomics: no
  session/thread object to manage for a single call.
* Multi-turn stays explicit: reuse the same session id across `runStream`
  calls (native `agent.session()`, or a retained `AriaCloudClient` session).
* Native SDK (in-process, local memo) and cloud client (SSE over HTTP) differ
  in transport but both hide the session id from the caller.
* Generated UniFFI bindings change only by dropping session from the public
  config; regenerate via `just ffi` and commit (rule 2). The hand-written
  `AriaCloudClient` files live alongside the generated bindings and are
  hand-maintained — they are NOT regenerated and MUST NOT be deleted by `just ffi`.
* READMEs (`bindings/swift/README.md`, `bindings/kotlin/agent-sdk/README.md`)
  document the session-less happy path plus the `AriaCloudClient` mint/stream
  flow.
